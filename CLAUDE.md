**WordPress embed (dev.dmagazine.com test post "Test inclusion"):** the page is injected inline (not an iframe) by a block with these fields: App URL `https://bobd2026.dmagazine.com/`, Asset base URL `https://bobd2026.dmagazine.com`, Bypass cache, and **SSR snapshot**. This deck is a client-rendered app (`support.js` + the `text/x-dc` script). **SSR snapshot works set to Yes** (Ricky confirmed on the live www.dmagazine.com post, Nov 24: tabs, cards and popups all work). An early test on dev.dmagazine.com (Nov 21) showed only static markup with Yes, but that was before the inline-safe rewrite and the logic bridge below; treat "Yes breaks the deck" as outdated. Keep Bypass cache on while testing. Things the embed relies on, all in the repo:
- **The block inlines `support.js` into a `<script>` tag when SSR snapshot is off** (no `src`). Raw `support.js` breaks there for two reasons, both fixed by `scripts/make-support-inline-safe.js`: (1) literal `<!--` followed by `<script` inside its strings/regexes put the HTML parser in the double-escaped script state, so the script swallowed the whole `<x-dc>` template and logic (nothing rendered); (2) the runtime fetches its own page source and takes the first `<x-dc` as the template start, and support.js's own `<x-dc` strings came first, so the template became a slice of support.js (script text on the page). The rewrite was proved equivalent by comparing the ASTs (62,974 nodes identical; only the spelling of 11 literals differs). Re-run it after any support.js re-export; check with `--check`.
- **The block may drop the inline logic script** (`<script type="text/x-dc" data-dc-script data-props=...>`, the `Component` class; it is not JavaScript so hosts treat it as removable). Symptom (seen on dev.dmagazine.com, Nov 21): hero and static sections render, no tabs, cards or hero fan, console shows `[dc-runtime] Root: {{ headCount }} never resolved` then `{{ status }}`. Reproduced exactly by removing that tag from a simulated inlined page. Fix: `scripts/make-support-inline-safe.js` also prepends a small ES5 **logic bridge** to support.js (between `bobd:logic-bridge` markers, replaced in place on re-runs). At DOMContentLoaded, if the tag is missing or empty and the app is on another origin, it does a synchronous XHR for the app's own `/` (index.html; CORS header in `vercel.json`), copies the tag (text and `data-props`) back into the page, and the runtime then boots normally. With the tag present it does nothing (0 requests). Base URL comes from `window.BOBD_BASE` or a host-rewritten `/assets/` URL inside `<x-dc>`.
- **The block rewrites every relative `src`, `href` and `poster` in the template with the asset base, and percent-encodes braces.** `src="{{c.img}}"` became `https://bobd2026.dmagazine.com/%7B%7Bc.img%7D%7D`, so the hole was lost (every image requested that one URL; every link, too). Reproduced exactly in a simulated block (Nov 21). **Rule for template edits: never put a bare `{{hole}}` in `src`, `href` or `poster`.** Use `data-bd-s="{{x}}"` (src), `data-bd-l="{{x}}"` (href) or `data-bd-p="{{x}}"` (poster); `hydrateUrls()`/`watchUrls()` (MutationObserver, runs before paint) copy them to the real attributes when React inserts or changes the element. The names are deliberately short so no `src=`/`href=` pattern can match them. Static, non-hole values (e.g. `src="/assets/pips/...svg"`) are fine: the block turns them into absolute URLs. The standalone page is identical (same URLs, same pixels once lazy images settle).
- `APP_BASE` (script, near `DATA_URL`) is derived from the `<script src="...support.js">` tag, else (support.js inlined, no src) from an `/assets/` URL the block rewrote inside the template, or `window.BOBD_BASE`, and `appUrl()` prefixes every root-relative path built in JS or read from `winners.json` (`img`, `v`, pips, fan photos, card backs). Cross-origin, the six `@font-face` rules are re-declared with absolute URLs.
- `vercel.json` sends `Access-Control-Allow-Origin: *` for `/` (the bridge reads index.html), `/data/*`, `/assets/fonts/*` and `/support.js`; without it the fonts and the JSON fetch are blocked from www/dev.dmagazine.com.
- CSS is scoped so it does not restyle the host: body styles only apply when `#dc-root` is a direct child of `<body>` (standalone), box-sizing and fonts are on `#dc-root`, and a type-selector reset (`div div :is(p,span,...){font-family:inherit...}`, specificity (0,0,3), beats a theme's bare `p{}`/`span{}` but loses to every class rule) stops theme element styles leaking in. Selectors like `.entry-content p` (class-level) would still win; fix those with a linked override CSS.
- **Theme CSS collisions found on dev.dmagazine.com (Nov 21, from the console diagnostic).** Only one class collides: the theme's `.step` (style.min.css: width 100%, margins, padding, shadow, radius) hit our "Pick a suit / Flip a card" steps. Fixed with `#dc-root .step{all:revert; ...our rules...}` (specificity beats the theme; `all:revert` drops anything the theme sets, even properties we could not see). The rest are bare-element rules from main_*.css (`a{display:inline-flex}`, `h1`/`h2`/`h3`/`h4` fonts and sizes, `button{outline:none}`, input borders) and the deck's own class rules already win over them; `.jlink` now sets `text-decoration:underline` and `.search input` sets `padding:1px 2px` explicitly so the theme's `a`/`input` rules cannot change them. A theme `.dmag-static-app-embed a svg ...{fill:none}` rule also matches 1,095 elements inside the deck (not yet understood). To find new collisions: run the snippet that lists theme rules matching `#dc-root *` (same-origin sheets only) and fix the class collisions the same way. Specificity alone cannot beat a theme rule that only ADDS properties we never set (shadow, margin): neutralise those per class.
- **The host's sticky nav covers the deck's sticky filter bar.** `.controls` sticks at `top:var(--bd-top,0px)`; `watchStickyOffset()` measures what is fixed/sticky at the top of the screen outside `#dc-root` (a few `elementsFromPoint` calls on scroll/resize, stacking up to four bars, e.g. WP admin bar + site nav) and sets `--bd-top` on `#dc-root`. A header that hides on scroll drops it back to 0. Standalone it stays 0. `.card,.row` scroll-margin also adds `--bd-top` so hash jumps clear the header. Tested with fake fixed/stacked/hiding headers, not the real dmagazine.com nav.
- The Adobe Fonts (Typekit) kit must list `www.dmagazine.com` and `dev.dmagazine.com` or Blackest falls back to a serif.
- Tested only against a simulated host page (different origin, serif theme CSS), not the real theme.

**Marfeel / GA4 signup tracking (Nov 25):** dmagazine.com has one central tracker, `util/conversion-tracking.js` in the theme (`/wp-content/themes/dmag/resources/assets/scripts/util/conversion-tracking.js`, public). It defines `window.dmagTrackConversion(type, meta)` (and the legacy alias `window.dmagMarfeelTrackConversion`): dedupes within 5 s by `type + meta.form_id`, pushes `{ event: 'dmag_conversion', conversion_type: type, ...meta }` to the dataLayer (GA4) and calls Marfeel Compass `compass.trackConversion(type, { meta })` inside `window.marfeel.cmd`. Types in use: `newsletter_signup` (default HubSpot form), `newsletter_signup_inline` (inline HubSpot form; the wrapper carries `data-mrf-conversion="newsletter_signup_inline"`), `newsletter_signup_modal`. Its HubSpot hooks (an `onFormSubmitted` callback or an `hsFormCallback` postMessage) never fire for our deck because our form posts to the HubSpot Forms API directly. So the deck calls the tracker itself: `trackConversion(MRF_CONVERSION, { form_id: HS_FORM, program: 'best-of-big-d-2026', list, tab })` in `index.html`, only after HubSpot answers 200 (`MRF_CONVERSION = 'newsletter_signup_inline'`). If the theme script is not on the page it sends the same dataLayer event and Marfeel call itself. **Do not add `data-mrf-conversion` to our `<form>`**: Marfeel's automatic tracking would also count every submit attempt (bad email, failed request). Marfeel docs: https://www.marfeel.com/docs/loyalty/track-conversions-and-subscriptions-with-the-sdk (`compass.trackConversion(name, { meta, value, scope, id })`). Tested here with stubs for the theme function, the Marfeel queue, and neither (success, HubSpot 400, bad email, honeypot); **not verified on the live page**: that `dmagTrackConversion` exists on the BOBD WordPress page, and that the conversion shows up in Marfeel and GA4. `data-mrf-recirculation="<module>"` on a block is a different thing (a recirculation module label) and is not set on our signup block. `www.marfeel.com` is in this environment's allowed hosts.

## Gotchas and how to test

- Run it locally with `python3 -m http.server` from the repo root and open it in Playwright (Chromium is preinstalled in the cloud sandbox). Block `dmagstatic`, `typekit` and `fonts.g` requests so the test is not slow, or expect broken images. In a cloud session the permission classifier has blocked this setup before; if it does, stop and ask rather than working around it.
- The Typekit CSS is unreachable from the sandbox. Read it in the user's Chrome if you need it.
- To test ads without the network, stub `window.googletag` before load (`addInitScript`) with `cmd.push(f)=>f()`, `defineSlot`, `display`, `destroySlots`, `pubads()`, `enableServices`, `setConfig`, and route `securepubads` to an empty JS file so `ads-off` does not trigger.
- The party-ticket popup opens on scroll and covers clicks. In tests, remove `.promo` or click through `evaluate(e => e.click())`.
- The page has a `MutationObserver` on `document.body` (`watchFit`) that reruns `fitNames()`, `fitBlurbs()` and `syncAds()` after DOM changes. There is a duplicate `componentWillUnmount` (the later one wins); harmless since the page never unmounts.
- Breakpoint for phones is 600px (grid is 2 columns, Wild Cards span both). Desktop grid is `auto-fill, minmax(250px, 1fr)` in a 1216px container (4 columns at full width).
- Do not hotlink images inside the old Design canvas; its CSP blocks them. This is no longer an issue on Vercel.
